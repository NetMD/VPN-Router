## 3. 정책이 걸리긴 했는가 (판단 근거)

정책이 걸렸다고 볼 근거가 있으나 **직접 확인하지는 않았다.**

| 신호 | 값 | 뜻 |
|---|---|---|
| 정책 추가 실패 코드 | 없음 | `IPV4_POLICY_ADD_FAILED` 등이 안 나왔다 |
| `cleanupOutcome` | `PASS` | 치울 소유 정책이 있었다는 뜻 |
| 사례 측정 시각 | 정책 적용 시각 뒤 | 관문(`CAPTURE_BEFORE_POLICY`)에 안 걸렸다 |
| `beforeAfterFingerprint` | `MATCH` | 경로표가 안 바뀌었다 (WFP 는 원래 경로표를 안 건드린다) |
| `liveChangedNetwork` | `false` | 같은 뜻 |

**안 한 것**: 정책이 걸린 동안 `netsh wfp show state` 를 떠서 조건(앱 ID · 다음 홉 인터페이스)을 직접 읽지 않았다. 그래서 아래 두 갈래가 안 갈렸다.

## 4. 남은 갈래 두 개 (이 문서가 못 가르는 것)

| # | 갈래 | 뜻 |
|---|---|---|
| **가** | 정책은 걸렸는데 **다음 홉 지정이 안 먹었다** | 사용자 모드 WFP 연결 계층에서 인터페이스를 지정해도 실제 라우팅이 안 바뀐다 = **구조적 한계** |
| **나** | **앱 신원이 안 맞았다** | 정책이 가리키는 실행 파일과 실제로 연결을 만든 프로세스가 어긋났다 = **고칠 수 있는 결함** |

**나 를 의심할 근거가 있다.** 2026-08-17 사전 감사에서 확인했듯 브라우저의 연결은 실행 파일 경로가 같은 **network service 자식 프로세스**가 만든다(실측: 실행기 22384 · 브라우저 뿌리 18700 · 연결 주인 18908). 경로가 같으니 WFP 앱 ID 는 맞아야 하지만, 실제로 그런지는 재지 않았다.

**가르는 방법**: 실기를 한 번 더 돌되 정책이 걸린 동안 `netsh wfp show state` 를 떠서 걸린 조건을 읽는다. 30분쯤 걸린다.

## 5. 이 결과를 어떻게 읽어야 하는가

**`verdict: FAIL` 을 "측정 실패"로 읽으면 안 된다.** FAIL 이 한 건이라도 있으면 전체가 FAIL 이다(설계). 여기서 FAIL 은 **"고른 앱이 기대한 경로로 안 갔다는 사실을 측정했다"** 는 뜻이다. 그것이 이 실기가 알고자 한 것이다.

전체 판정 구성: 64건 = PASS **1** · FAIL **1** · NOT_RUN **32** · INCONCLUSIVE **30**

| 구간 | 결과 | 근거 |
|---|---|---|
| IPv4 TCP 4건 | 실측 2 · `UNOBSERVED` 2 | 위 근거표 |
| UDP·QUIC·DNS 12건(IPv4) | `NEW_CONNECTION_NOT_OBSERVED` | 흐름 발생기가 브라우저에 URL 을 넘기는 방식이라 이 셋을 못 만든다 — **사례의 실패가 아니라 관찰 수단의 한계** |
| IPv6 16건 | `ENVIRONMENT_UNAVAILABLE` | 이 회선에 IPv6 전역 주소·경로가 없다 |
| 패키지 32건 | `NOT_RUN` | 패키지 신원 증명 코드 미구현 (`R3-DEC-05` 미결) |
